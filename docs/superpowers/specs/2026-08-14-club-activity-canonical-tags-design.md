# 동아리 활동 인증 태그 정규화 설계

## 목적

동아리 활동 인증 작성 시 운영진이 등록한 현재 동아리만 선택하게 하고, 운영진이 동아리명을 수정하면 기존 활동 인증의 태그에도 최신 공식명이 자동 반영되게 한다. 운영 종료된 동아리는 신규 선택지에서 제외하되 과거 활동 인증에는 마지막 공식명을 유지한다.

현재 활동 중인 공식 동아리는 다음 7개다.

- `SG_LLM`
- `알바트로스냅`
- `서강의 봄`
- `서뽈링`
- `서강와인`
- `인간지능투자`
- `FC리턴윈`

## 범위

- `club-promo` 게시글을 동아리 이름의 단일 원본으로 사용한다.
- `club-activity` 활동 인증의 선택 대상 검증과 태그 해석을 강화한다.
- 기존 활동 인증을 공식 동아리 원본에 연결하는 일회성 정리 도구를 제공한다.
- API 계약과 관련 테스트를 갱신한다.

## 범위 제외

- 화면 구조, 컴포넌트 배치, 스타일, 문구, 사용자 조작 순서는 변경하지 않는다.
- 별도 `clubs` 테이블이나 신규 동아리 관리 화면을 만들지 않는다.
- 스터디 및 네트워킹 활동 인증의 동작은 변경하지 않는다.
- 운영진 동아리 게시글에 필요한 대표 이미지와 신청 URL을 자동 생성하지 않는다.

## 선택한 방식

활동 인증에 저장된 이름 문자열을 원본으로 사용하거나 이름 변경 시 모든 활동 인증 행을 일괄 수정하지 않는다. 이미 저장 중인 `metadata.activity_source_post_id`로 운영진의 `club-promo` 게시글을 참조하고, 읽기 응답에서 원본의 현재 제목을 `activity_source_title`로 제공한다.

이 방식은 기존 게시판 중심 구조를 유지하면서 이름 변경 때 대량 쓰기를 피한다. `posts.category`는 작성 당시 이름의 스냅샷이자 연결이 손상된 기존 기록을 위한 fallback으로 유지한다.

## 활성 동아리 기준

- 신규 작성 및 동아리 변경 선택지에는 삭제되지 않은 `status = published`의 `club-promo` 게시글만 포함한다.
- 관리자 계정으로 활동 인증을 작성해도 `draft`와 `hidden` 게시글은 선택지에 포함하지 않는다.
- 현재 7개 공식 동아리가 운영진 원본에 정확한 제목으로 존재하고 공개 상태인지 배포 전 데이터 점검에서 확인한다.
- 운영 종료 처리는 원본 게시글의 기존 삭제 기능을 사용한다. 삭제는 soft delete로 남아 마지막 공식명을 보존하며, 해당 동아리는 신규 선택지에서 제외된다.

## 작성 및 수정 흐름

1. 기존 활동 인증 선택 UI는 `club-promo`의 공개 게시글을 조회한다.
2. 사용자는 현재와 같은 선택 시트에서 동아리를 선택한다.
3. 클라이언트는 선택한 게시글 ID를 `metadata.activity_source_post_id`로 전송한다.
4. 서버는 `club-activity` 생성 또는 동아리 변경 요청에서 다음 조건을 검증한다.
   - 현재 클라이언트가 보내는 10진수 문자열을 양의 정수 ID로 해석할 수 있는지 확인한다.
   - 대상 게시글이 실제 `club-promo` 게시판에 속하는지 확인한다.
   - 대상이 삭제되지 않은 공개 게시글인지 확인한다.
5. 서버는 검증된 원본 제목으로 `posts.category`를 정규화한다. 클라이언트가 보낸 임의 동아리명은 신뢰하지 않는다.
6. 기존 활동 인증을 다른 항목만 수정하면서 `activity_source_post_id`를 변경하지 않은 경우, 연결된 동아리가 이후 운영 종료되었더라도 수정을 허용한다. 운영 종료된 동아리를 신규 선택하거나 다른 글에 새로 연결하는 것은 허용하지 않는다.

유효하지 않은 원본 ID, 잘못된 게시판, 비공개 또는 삭제된 신규 선택에는 `422 INVALID_ACTIVITY_SOURCE`를 반환한다. 검증 실패 시 게시글이나 첨부 데이터는 일부만 저장되지 않는다.

## 태그 표시 흐름

- 활동 인증 목록 응답은 현재 페이지의 `activity_source_post_id`를 모아 한 번의 추가 조회로 원본 제목을 구한다.
- 활동 인증 상세 응답도 같은 규칙으로 연결된 원본 제목을 제공한다.
- 연결된 원본은 운영 종료 후에도 데이터베이스에 남아 있는 마지막 제목을 읽어 과거 태그에 사용한다. 현재 삭제는 soft delete이므로 마지막 공식명 보존이 가능하다.
- 클라이언트의 동아리 활동 인증 태그 우선순위는 다음과 같다.
  1. API의 `activity_source_title`
  2. 구체적인 `post.category`
  3. 구체적인 `metadata.legacy_activity_name`
  4. `동아리 활동 인증`
- 태그 컴포넌트의 마크업과 스타일은 유지하고 표시 문자열을 결정하는 로직만 변경한다.
- 운영진이 `club-promo` 제목을 수정하면 다음 목록·상세 조회부터 연결된 모든 기존 활동 인증 태그에 새 이름이 표시된다. 활동 인증 행을 일괄 수정하지 않는다.

## 기존 데이터 정리

재실행 가능한 관리 스크립트를 dry-run 기본값으로 제공하고, 명시적인 `--apply`에서만 변경한다.

정리 절차는 다음과 같다.

1. 공개 상태인 `club-promo` 원본을 읽어 제목을 Unicode NFKC로 정규화하고 앞뒤 공백 제거 및 연속 공백 축소 후 비교한다.
2. 이미 유효한 `activity_source_post_id`가 있는 활동 인증은 해당 연결을 유지하고 `category` 스냅샷만 현재 공식명으로 정규화한다.
3. 연결이 없거나 잘못된 기존 글은 `category`와 `metadata.legacy_activity_name`을 공식 제목 및 운영진이 검토한 `별칭 -> 공식 제목` JSON 파일과 비교한다.
4. 정확히 하나의 원본으로 확정되는 글만 `activity_source_post_id`와 `category`를 갱신한다.
5. 일치하지 않거나 둘 이상과 일치하는 글은 변경하지 않고 게시글 ID, 기존 이름, 실패 이유를 보고한다.
6. 전체 작업은 하나의 트랜잭션에서 실행하며 적용 건수, 유지 건수, 미확정 건수를 출력한다.

스크립트는 동아리 원본 게시글을 새로 만들지 않는다. 대표 이미지와 신청 URL이 필요한 원본 등록은 기존 운영진 관리 흐름에서 수행한다.

## 호환성과 회귀 방지

- `activity_source_title`은 선택 응답 필드이므로 이전 클라이언트는 기존 `category`로 계속 표시할 수 있다.
- 기존 `category`와 레거시 이름을 삭제하지 않아 연결이 손상된 기록도 표시할 수 있다.
- 스터디와 네트워킹 활동 인증의 선택, 저장, 태그 규칙은 그대로 유지한다.
- 게시글 작성 화면의 선택 시트, 완료 화면, 이미지·날짜·참가자·계좌 입력 로직은 변경하지 않는다.

## 검증

백엔드 테스트는 다음을 확인한다.

- 공개 `club-promo` 원본을 선택한 활동 인증이 서버 공식명으로 저장된다.
- 임의 `category`, 존재하지 않는 ID, 다른 게시판 ID, 비공개·삭제된 신규 원본을 거부한다.
- 운영 종료된 기존 연결을 유지한 채 다른 활동 인증 필드를 수정할 수 있다.
- 목록 조회가 연결된 최신 원본 제목을 내려주고 N+1 조회를 만들지 않는다.
- 운영 종료된 원본은 과거 글에 마지막 공식명을 제공한다.
- 정리 스크립트가 확정 가능한 항목만 변경하고 미확정 항목을 보고하며 재실행해도 같은 결과를 낸다.

프런트엔드 테스트는 다음을 확인한다.

- 동아리 태그가 `activity_source_title`을 우선한다.
- 원본 제목이 없을 때 기존 `category`와 레거시 이름으로 안전하게 fallback한다.
- 스터디와 네트워킹 태그 동작이 바뀌지 않는다.
- 선택 UI에는 공개 동아리만 요청되며 기존 렌더링 구조와 사용자 동작이 유지된다.

전체 백엔드 테스트와 프런트엔드 테스트·typecheck를 실행해 다른 게시판과 활동 인증 흐름의 회귀가 없는지 확인한다.

## 배포 순서

1. 호환 가능한 API 응답과 서버 검증, 프런트엔드 태그 해석을 배포한다.
2. 운영진 원본에 공식 7개 동아리가 정확한 제목과 공개 상태로 등록되어 있는지 dry-run으로 점검한다. 누락 또는 추가 공개 동아리가 있으면 적용하지 않고 목록을 보고한다. 7개 이름은 이번 정리 작업의 기대 데이터로만 사용하며 런타임 선택 로직에 하드코딩하지 않는다.
3. 기존 데이터 정리 스크립트를 dry-run으로 검토한 뒤 적용한다.
4. 미확정 항목은 운영진이 원본을 확인한 후 별칭표에 명시적으로 추가해 다시 적용한다.
5. 활동 인증 작성 선택지와 기존 태그가 공식명으로 표시되는지 smoke test한다.
